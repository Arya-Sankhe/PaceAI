Bottom line. A VFFS is a master-cycle machine: the axis in the synchronized critical path caps the whole line's rate. The good news is the tags we already poll contain enough signal to identify that constraint before it derates us — by watching each axis's rpm-to-speed coupling ratio and its current-per-rpm load. Most recoverable output sits in two places: closing the actual_speed ↔ set_speed gap (stability, not control) and fixing the one axis or heater zone that deviates first as speed rises.

02The previous-state gap

When no machine is connected, finding "the live snapshot from a previous time" is limited — and this is the single biggest structural constraint on any speed work.

Nothing is persisted

History lives in RAM only: every 1 s poll kept for 15 minutes (fine), downsampled to one sample/minute for 7 days (coarse). A process restart wipes both.

Evidence machine_source.py:86-90, _remember() :165

Migration note "telemetry … is not persisted" — migrations/001_initial_schema.sql:8

When disconnected, snapshot() returns the last good read with freshness="disconnected" and an age — but only if that process actually connected before. Otherwise values arrives as {} (machine_source.py:228-245).

The only durable record of prior machine state is the commissioning grab:

Captured server_time 2026-07-08T17:17:23

Source IP 192.168.213.1

Implication Without persistence, the speed tracking below can run live but cannot build baselines across restarts. Persistence is the enabler — and it is independent of any write path.

03If one servo underperforms, does it slow the whole machine?

Yes — if it is in the synchronized critical path. And the data tells us which axes those are.

Most VFFS axes are cam/eCam-coupled to a single master angle. At a given bags/min, each coupled axis has a required rpm (fixed gear ratio) and a required torque. If an axis can't reach required rpm (following error) or exhausts torque (current saturation), the master derates or faults — the whole line slows. Some axes are not coupled (unwind tension, auxiliaries) and can underperform without directly capping rate.

So the operative question is not "is a drive slow" but "is that drive the constraint, and how do I see it before it derates me?" We can compute that from tags already polled:

SignalFormulaReads as
Coupling ratioR = {ax}_rpm / actual_speedFlat → axis is cam-coupled (critical path). Wandering → decoupled.
Constraint onsetdeviation of R from its learned baseline as actual_speed risesFirst axis to deviate is the emerging bottleneck.
Torque headroom{ax}_current vs its rpm/current curveCurrent climbing off the curve = running out of headroom.
True cycle rateΔadvance_cycle_dump / ΔtReal bags/min from a cycle counter — independent of the HMI speed number.
Fault signature{ax}_error_active + {ax}_error_id + _error_textWhich axis tripped, joinable to speed at that instant.

For a VFFS the usual critical axes are FF (film feed) — sets film advance per cycle, CS (cross seal) — seal dwell eats cycle time, VS (vertical seal) — tied to film speed, and UW (unwind) indirectly via tension. PK / BX matter only if their motion sits inside the cycle window.

04Deviation catalogue — what costs output, and the tag that shows it

DeviationWhy it costs outputRevealed by
Seal-dwell constraint top suspect Marginal seals force longer dwell → cyclic rate drops; the classic VFFS ceiling. {zone}_output high while {zone}_temp sags below set; {zone}_tol flips false clustering at higher speed.
Film tension / tracking Film slip → can't hold speed, reject rate rises. A common hidden derate. dancer_pos off its idle band, uw_current rising, web_roll_center wandering.
Mechanical drag Load builds → axis becomes the constraint; leading maintenance signal. {ax}_current creeping at constant {ax}_rpm / {ax}_temp.
Micro-stops Many short stops destroy availability more than one long stop. Rise in alarm_count per advance_cycle_dump delta.
Configured headroom set_speed < max_speed is deliberately unused capacity. set_speed vs max_speed vs actual_speed gap decomposition.

Performance loss decomposes three ways

actual / set   →  production inefficiency, drift, micro-stops
set / max      →  headroom the line is configured NOT to use
actual / max   →  the OEE performance figure the HMI reports

The first ratio is where recoverable output usually hides. The second is the safe-to-explore territory, gated by the constraint detector.

05Safe ways to unlock output — ranked by risk

  1. Close the actual↔set gap. No process change — pure stability: film tension, seal heat, stop reduction.
  2. Hunt the constraint at current set_speed. Find the axis/zone that deviates first and fix it mechanically. No control change.
  3. Raise set_speed only while guardrails hold. Quality flat (*_tol flips and rejects not rising) AND no axis's current/rpm ratio declining. This is a supervised trial — the point where a write path would eventually help, but the analysis stands alone first.
  4. Improve heater control to shorten dwell. Better temperature stability buys cycle time without touching speed.

Safety guardrail: faster sealing can produce weak seals — running quicker is only "safe" while reject rate and seal-zone tolerance stay flat. Every speed trial must carry a quality abort condition.

06Speed tracking design

Per snapshot, record and roll these series (all tags we already poll):

  • actual_speed, set_speed, max_speed
  • every {ax}_rpm, {ax}_current
  • every {zone}_temp, {zone}_output, {zone}_tol
  • dancer_pos, advance_cycle_dump, alarm_count

Then compute rolling, and surface the first one to degrade as speed rises:

cycle rate from counter per-axis coupling ratio per-axis current-per-rpm heater in-tol % stops per 1000 bags

This is a small pure function over history points, testable against the dummy source — a good first build because it directly answers "which drive is limiting us."

07Data gaps worth closing

No air-pressure tag

"Air Pressure Error" is a top unplanned reason, yet no pressure signal is in the manifest — the report can see the symptom but not the cause.

No per-cycle timing/position

No cycle-time or per-cycle position tag; advance_cycle_dump is the only cycle proxy. Cycle-level timing would sharpen constraint detection a lot.

No telemetry persistence

RAM-only history (15 min fine / 7 day coarse, wiped on restart) means no cross-restart baselines or trend tracking.

TBD production tags

count_good, count_bad, running, fault_code are unverified ::TBD: nodes — quality-vs-speed needs them verified on site.

08Suggested next steps

  1. Build the speed_tracking analyzer — coupling ratios + constraint detection + cycle-rate-from-counter, as a pure function over source.history(...), wired into the cockpit and the shift report.
  2. Add telemetry persistence — a samples table fed from the _run() loop, so tracking survives restarts and baselines can form.
  3. Verify the ::TBD: nodes on site — unlocks quality-vs-speed analysis.
  4. Honor fast/slow/event poll classes — lower PLC load, no resolution loss.

Writes to the machine remain out of scope for this analysis — the recommended path starts with advisory output and only reaches supervised writes once the constraint detector is trusted.
