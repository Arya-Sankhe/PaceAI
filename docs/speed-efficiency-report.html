Speed & Efficiency Analysis

Can we safely unlock more output from the machine — and what the data already tells us.

Will one underperforming servo slow the whole machine? Yes — but only if it sits in the synchronized critical path, and the data tells us which axes those are.

A VFFS is a master-cycle machine: most axes are cam/eCam-coupled to one master angle. At a given bags/min, each coupled axis has a required rpm (fixed gear ratio) and a required torque. If an axis can't hit its required rpm (following error) or runs out of torque (current saturation), the master derates or faults — the whole line slows. Non-coupled axes (unwind tension, auxiliaries) can underperform without directly capping rate.

So the real question isn't "is one drive slow" — it's "is that drive the constraint, and can I see it before it derates me?" We can compute that from the tags we already poll:

01Small components that can slow the whole line

A drive is usually the messenger, not the culprit — it faults or saturates because something small upstream let go. Any component that lets one part of the cycle slip will derate the whole master cycle, and several are trackable with tags we already poll.

Four "derate signatures"

  • Command without effect — output/command high, result missing. Heater cartridge, SSR, valve, clutch.
  • Load creep at constant speed — current rising at steady rpm. Bearing, belt, chain, tension drag.
  • Command/feedback divergence — sensor drifts from what is commanded. Thermocouple, encoder, potentiometer.
  • Intermittent event cluster — stop bursts, not a steady derate. Sensor, relay, pneumatic.

Sleeper asset: the OEE unplanned-reason arrays (udt_0..10 + unplanned_dt_sorted_titles) are the HMI's own ranked failure taxonomy — Air Pressure Error, Print Mark Error, Material Chokeup, Printer Error, P.I.S Error. That list is the machine telling you which small components fail most; cross-reference it against the sensor trends to get root cause, not just symptom.

When an axis looks slow, separate three cases: drive-internal ({ax}_error_id set and/or {ax}_temp high → drive/cooling), mechanical load ({ax}_current high, no error → bearing/belt/tension), external (no current or temp anomaly, command never rises → setpoint, film, or upstream). Only the first is a drive problem.

03Safe ways to unlock output — ranked by risk

  1. Close the actual↔set gap. No process change — pure stability (tension, seal heat, stop reduction).
  2. Hunt the constraint at current set_speed. Find the axis/zone deviating first and fix it mechanically, not by control.
  3. Raise set_speed only while guardrails hold. Quality flat (tol-flips and rejects not rising) AND no axis's current/rpm ratio deteriorating. A supervised trial — where a write path would eventually help, but the analysis works standalone first.
  4. Improve heater control to shorten dwell. Better temp stability buys cycle time without touching speed.
Safety guardrail: faster sealing can produce weak seals. Speed is only safe while reject rate and seal-zone tolerance stay flat — every trial needs a quality abort condition.

04Speed tracking design

Per snapshot, record: actual_speed, set_speed, max_speed, all {ax}_rpm/{ax}_current, all {zone}_temp/output/tol, dancer_pos, advance_cycle_dump. Then compute rolling — the first series to degrade as speed rises is the constraint:

  • Cycle rate from the counter
  • Per-axis coupling ratios
  • Per-axis current-per-rpm
  • Heater in-tolerance %
  • Stops per 1000 bags

That's a small pure function over history points — testable against the dummy source.

05Data gaps worth flagging

  • No air-pressure tag — yet "Air Pressure Error" is a top unplanned reason. Symptom visible, cause not.
  • No per-cycle position / cycle-time tag — both would sharpen speed analysis a lot (advance_cycle_dump is the only cycle proxy).
